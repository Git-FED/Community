### 200 words

FEDPromptly is an open ecosystem focused on browser-native tools, embeddable code, digital assets, and cross-platform publishing. The organization’s work is aimed at creators and teams that want to build, share, and distribute useful web experiences without treating the browser as a second-class delivery channel.

FED-Shell extends that idea into app packaging. It is positioned as a universal URL-wrapper build workflow: a team starts with an existing web URL, defines the application’s release details in a versioned project, and runs GitHub Actions to produce supported installable app artifacts. The goal is not to claim that every website should become a native app, or that every build is automatically store-ready. The goal is to give web-first teams a more repeatable starting point for distribution across supported platforms.

FED-Shell is relevant to product teams, agencies, makers, and internal-tool builders who already have a web experience and want an installed-app path without immediately committing to a separate native codebase. Users remain responsible for testing the target experience, managing signing and developer accounts, making accurate privacy disclosures, and complying with each distribution channel’s policies.

## Interview prep: candid answers

### “Why not just make a native app?”

> For many products, a dedicated native application is the right answer. FED-Shell is for the cases where the web product already delivers the value and the team wants a repeatable packaging and distribution path without beginning from zero. The decision depends on the product’s need for native features, offline behavior, performance, and user expectations.

### “Can any website become an app-store app?”

> A build can be generated from a URL, but app-store eligibility is a separate question. Quality, functionality, ownership, privacy, signing, and current store policy all matter. We tell users to test and review those requirements before they plan a launch.

### “Is this a low-code product?”

> FED-Shell reduces packaging work, but it is not a substitute for ownership. Teams still manage their web product, release credentials, QA, and policy compliance. The best description is a developer-friendly, CI-centered workflow rather than a magic conversion button.
